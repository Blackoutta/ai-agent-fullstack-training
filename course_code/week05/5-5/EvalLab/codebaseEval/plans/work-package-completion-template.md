# 功能补全工作包模板（Feature Completion WP Template）

> 当开发任务功能开发不全时，用于重新读取需求和设计文档进行功能补全。

```markdown
# WP-XXX-complete-<功能简述>

## 1. 补全信息

| 属性 | 值 |
|------|-----|
| 关联开发任务 | <TASK-XXX> |
| 负责角色 | <后端开发/前端开发/移动端开发/数据库工程师/测试/运维> |
| 补全原因 | <功能缺失/实现不完整/需求变更/设计遗漏> |
| 优先级 | <高/中/低> |

## 2. 缺失功能描述

### 功能需求
<描述缺失的功能，引用需求文档中的具体条目>

### 现有实现分析
- 已实现部分：<列出已实现的功能点>
- 缺失部分：<列出缺失的功能点>
- 差距分析：<分析现有实现与需求之间的差距>

### 影响范围
- 影响模块：<哪些模块受影响>
- 影响接口：<哪些接口需要新增或修改>
- 影响数据模型：<哪些表结构需要变更>

## 3. 复现与验证

### 验证步骤
1. <步骤1：验证现有功能>
2. <步骤2：触发缺失功能场景>
3. <步骤3：观察缺失现象>

**缺失确认**：<已确认/待确认>

## 4. 根因分析

### 直接原因
<代码层面的缺失原因>

### 根本原因
<导致功能缺失的深层原因>

### 相关代码
- 文件：<path/to/file.java>
- 行号：<L100-L120>

## 5. 补全方案

### 补全策略
<简述补全思路>

### 实现范围
| 文件 | 修改类型 | 说明 |
|------|---------|------|
| path/to/file.java | 新增 | <具体新增内容> |
| path/to/file.java | 修改 | <具体修改内容> |
| path/to/test.java | 新增 | <测试用例> |

### 设计对齐
- 需求文档引用：<引用需求文档中的具体条目>
- 设计文档引用：<引用设计文档中的具体章节>
- 接口对齐：<与现有接口的兼容性>

### 风险评估
- 影响范围：<本次补全是否可能影响现有功能>
- 回归风险：<高/中/低>
- 需要额外测试：<哪些功能需要回归测试>

## 6. 验收标准（可勾选）

- [ ] 功能已补全：缺失功能已实现并可正常使用
- [ ] 需求对齐：补全的功能符合需求文档要求
- [ ] 设计对齐：补全的实现符合设计文档规范
- [ ] 接口兼容：新增接口与现有接口兼容
- [ ] 单元测试已补充：新增/修改的代码有对应测试
- [ ] 回归测试通过：受影响功能的回归测试通过
- [ ] 无新问题引入：未引入新的 bug 或性能问题
- [ ] 代码审查通过：符合代码规范和设计要求

## 7. 三色权限标签

- ✅ Always：<AI 可自动执行>
- ⚠️ Ask First：<需用户确认>
- 🚫 Never：<禁止>

## 8. 关联信息

- 关联需求文档：<引用需求文档路径>
- 关联设计文档：<引用设计文档路径>
- 关联工作包：<如果有相关功能开发工作包>
```

## 填写说明

1. **补全信息**：记录补全的基本信息
2. **缺失功能描述**：清晰描述缺失的功能和现有实现差距
3. **复现与验证**：验证缺失功能的存在
4. **根因分析**：区分直接原因和根本原因
5. **补全方案**：明确实现范围和设计对齐
6. **验收标准**：可勾选的验收项
7. **三色标签**：明确 AI 执行权限

## 命名规范

- 文件名格式：`WP-XXX-complete-<功能简述>.md`
- 示例：`WP-007-complete-用户导出功能.md`

## 与功能开发工作包的区别

| 维度 | 功能开发工作包 | 功能补全工作包 |
|------|--------------|--------------|
| 重点 | 新功能实现 | 缺失功能补全 |
| 起点 | 需求文档 | 现有实现 + 需求文档 |
| 缺失分析 | 不需要 | 必须详细填写 |
| 根因分析 | 不需要 | 必须填写 |

## 与 Bug 修复工作包的区别

| 维度 | Bug 修复工作包 | 功能补全工作包 |
|------|--------------|--------------|
| 问题类型 | 功能异常/错误 | 功能缺失/不完整 |
| 触发条件 | Bug 报告 | 功能审查/需求验证 |
| 复现步骤 | 必须详细填写 | 验证缺失即可 |
| 根因分析 | 代码错误 | 实现遗漏/需求偏差 |
