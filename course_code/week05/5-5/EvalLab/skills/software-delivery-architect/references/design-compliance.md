# 设计符合性保障机制

> 本文档是 SKILL.md 的详细说明，执行时请以 SKILL.md 为准。

> 为确保研发严格按照设计方案实现，建立**事前预防、事中控制、事后验证**三重保障机制。

## 事前预防：设计方案必须明确可验证

### 设计文档要求

- 接口设计必须精确到路径、参数名、参数类型、返回值格式、状态码
- 数据库设计必须精确到表名、字段名、字段类型、约束、索引
- 目录结构必须精确到每个文件和包的职责说明
- 技术选型必须明确到具体的库名和版本号

### 生成设计审查检查单

- 架构师必须在生成设计文档时同步更新 `$CHECK_DIR/02-design.md`
- 检查单必须包含每个设计决策的验收标准
- 研发人员在开发前必须阅读并理解检查单

## 事中控制：开发过程检查点

### 开发前确认（必须执行）

- 架构师必须向研发人员介绍框架结构和使用方式
- 研发人员必须确认理解后方可开始编码
- 确认内容记录到 `$CHECK_DIR/` 目录下

### 工作包自检清单（每个工作包完成后）

- 目录结构是否与设计文档一致
- 模块划分是否与设计文档一致
- 接口定义是否与 API 设计文档一致（路径、参数、返回值）
- 数据模型是否与数据库设计文档一致（表名、字段、类型）
- 命名规范是否与设计文档一致（包名、类名、方法名）
- 技术选型是否与设计文档一致（不得引入未批准的依赖）
- 配置方式是否与设计文档一致
- 如发现不一致，必须停止开发并询问架构师

### 沟通机制（贯穿开发全程）

- 研发人员遇到设计问题必须通过 `question` 工具向架构师提问
- 不得擅自调整任何设计决策
- 如需调整设计，必须说明原因，经架构师评估同意后方可调整
- 重要沟通内容记录到 `$CHECK_DIR/` 目录下

## 设计方案调整流程

如研发人员发现设计方案存在问题或有更好的实现方式：

1. **停止开发**：不得擅自调整，立即停止当前工作
2. **提出申请**：通过 `question` 工具向架构师提出调整请求
3. **说明原因**：必须说明调整原因和预期效果
4. **架构师评估**：架构师评估调整的影响范围
5. **决策记录**：同意调整则更新设计文档，拒绝则维持原方案
6. **同步更新**：如同意调整，需同步更新相关设计文档和检查单
7. **通知相关方**：通知所有受影响的研发人员
