# 软件交付流水线 - 后端开发角色

> 后端开发负责实现后端业务代码，执行阶段0→阶段3→阶段4→阶段5→阶段6。

---

## 阶段0特殊处理（后端开发直接触发）

当通过 `/software-delivery-backend` 直接触发时，**跳过步骤1角色确认**，因为角色已确定为后端开发。

执行流程调整为：
1. **步骤0：路径确认** - 使用 `ui-standards §1.1` 模板
2. **步骤1：角色确认** - ⏭️ **跳过**（角色已确定为后端开发）
3. **步骤2：前置条件检查** - 检查架构类型、设计文档、代码框架
4. **步骤3：展示流水线状态** - 使用 §2.1 模板展示当前流水线状态

角色确认后直接展示：
```
**👤 角色确认**
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
当前角色：后端开发
执行阶段：阶段0 → 阶段3 → 阶段4 → 阶段5 → 阶段6
核心职责：实现后端业务代码
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 前置条件检查（必须执行）

在开始编码前，必须检查以下前置条件：

### 检查清单

1. **架构类型已确认**：`$CHECK_DIR/00-env/architecture-decision.md` 存在
2. **设计文档已生成**：`$DESIGN_DIR` 下有实际设计文档（排除模板文件）或 `$PLANS_DIR/DES-*.md` 存在
3. **代码框架已搭建**：项目目录结构、基础配置已就绪

### 不满足时的处理

- 若架构类型未确认：用 `question` 工具提醒用户先执行架构师角色完成阶段0步骤4
- 若设计文档未生成：用 `question` 工具提醒用户先执行架构师角色完成阶段2/3
- 若代码框架未搭建：用 `question` 工具提醒用户先执行架构师角色完成阶段3

## 框架边界识别

1. 查看架构师提供的框架使用说明，了解目录结构、模块职责、开发规范
2. 识别框架层和业务层的边界：
   - **框架层**（common、config、utils、mapper）由架构师维护
   - **业务层**（service、controller、entity、dto、vo）由后端开发实现
3. 框架层代码由架构师维护，业务层代码由后端开发实现

## 阶段3：编码实现

### 开发流程（严格按照设计方案）

**步骤0：选择开发任务（必须执行）**

在开始编码前，必须先询问用户要实现哪个TASK。使用 `ui-standards §1.6` 开发任务选择模板，选项根据 `$PLANS_DIR/TASK-*.md` 的实际文件列表动态填充。

```json
{
  "questions": [
    {
      "question": "请选择要实现的开发任务：",
      "header": "开发任务选择",
      "options": [
        {"label": "TASK-001", "description": "系统基础设施 - 认证、组织架构、用户、角色权限、部门设置、参数管理"},
        {"label": "TASK-002", "description": "任务管理核心 - 模板维护、任务创建发布、任务处理流转、催办强制完成"},
        {"label": "TASK-003", "description": "统计报表与驾驶舱 - 仪表盘、任务统计、科室及时率、考核指标报表"},
        {"label": "TASK-004", "description": "系统辅助功能 - RPA邮件解析、日志审计、批处理调度、代理配置、通知管理"}
      ]
    }
  ]
}
```

**注意**：如果用户通过命令行参数 `--task=N` 指定了TASK，则跳过此步骤，直接使用指定的TASK。

**步骤1-N：实现业务代码**

1. 在架构师搭建的代码框架基础上，**严格按照设计方案**实现业务功能
   - 设计依据优先级：`$PLANS_DIR/DES-*.md`（开发任务设计）> `$DESIGN_DIR`（系统设计）
   - 两者同时存在时以开发任务设计为准；两者都不存在时，必须等待架构师完成设计
2. 遵循框架的目录结构、命名规范、编码规范
3. 使用框架提供的公共组件和工具类，避免重复造轮子
4. **不得偏离设计方案**：如设计方案规定使用 MyBatis-Plus，则不得擅自改用 JPA

### 编码步骤

依据：`DES-*-api.md` + `DES-*-db.md`

1. pom.xml配置
2. application.yml
3. schema.sql
4. 业务代码（Service/Mapper/Controller）
5. 单元测试代码（用户选择"编写单元测试"时执行，见下方规范）
6. **展示交互式选项（§1.15）**

### 单元测试代码编写规范

**触发方式**：用户在 §1.15 交互式选项中选择「编写单元测试」

**后端单元测试规范**：
- 框架：JUnit 5 + Mockito
- 测试文件位置：`$DELIVER_DIR/backend/src/test/java/com/xiaomi/mimo/{service}/`
- 命名规范：`{ClassName}Test.java`
- 覆盖范围：核心业务方法（正常流程+异常流程+边界条件）
- 覆盖目标：行覆盖率≥80%，分支覆盖率≥70%

**测试代码结构**：
```java
@SpringBootTest
class {ClassName}Test {
    @MockBean
    private {Dependency} dependency;
    
    @Autowired
    private {ServiceClass} service;

    @Test
    void testNormalFlow() { ... }
    
    @Test
    void testExceptionFlow() { ... }
    
    @Test
    void testBoundaryCondition() { ... }
}
```

**测试代码交付路径**：`$DELIVER_DIR/backend/src/test/java/`

**执行后处理**：测试代码编写完成后，自动执行设计符合性审查和代码质量审查

### 并行策略

| 步骤 | 执行方式 | 说明 |
|------|----------|------|
| 读取DES文件 | subagent | 文件读取 |
| 生成Service代码 | subagent | 可并行生成多个Service |
| 生成Mapper代码 | subagent | 可并行生成多个Mapper |
| 生成Controller代码 | subagent | 可并行生成多个Controller |
| 生成单元测试 | subagent | 可并行生成多个测试类 |

并行示例：
```
同时派发3个subagent：
- SubAgent 1：生成UserService + UserMapper + UserController
- SubAgent 2：生成RoleService + RoleMapper + RoleController
- SubAgent 3：生成OrgService + OrgMapper + OrgController
```

### 框架调整请求

1. 如需调整框架结构，需与架构师协商
2. 通过 `question` 工具向架构师提出调整请求，说明调整原因和预期效果
3. 架构师评估影响后，决定是否调整框架
4. **未经架构师同意，不得擅自调整任何设计决策**

### 沟通机制

1. 遇到框架相关问题时，及时与架构师沟通
2. 通过 `question` 工具向架构师提问，架构师需及时响应
3. 重要问题需记录在 `$CHECK_DIR/` 目录下，便于追溯

## 迭代级审查（强制）

> **核心原则**：每个开发任务（TASK-XXX）是一个迭代。编码完成后，使用 `ui-standards §1.15` 模板展示交互式选项，让用户选择下一步操作。

### 完整迭代流程

```
后端编码 → 展示交互式选项（§1.15） → 根据选择执行对应操作
```

### 交互式选项（使用 §1.15 模板）

**询问时机**：编码完成后

**询问模板**：使用 `ui-standards §1.15` TASK完成后下一步选择模板

| 选项 | 执行动作 | 完成后处理 |
|------|----------|-----------|
| 设计符合性审查（推荐） | 执行设计符合性审查 | 移除「设计符合性审查」选项 |
| 代码质量审查 | 执行代码质量审查 | 移除「代码质量审查」选项 |
| 编写单元测试 | 执行单元测试 | 移除「编写单元测试」选项 |
| 继续下一个TASK | **允许跳过审查**，直接进入下一个TASK | 进入下一个TASK |
| 进入最终审查 | **允许跳过审查**，直接进入阶段6+7 | 进入最终审查 |
| 暂停流水线 | 保存当前状态 | 流水线暂停 |

**推荐流程顺序**：设计符合性审查 → 代码质量审查 → 编写单元测试

### 单元测试（可选，由研发人员决定）

**触发方式**：用户在交互式选项中选择「编写单元测试」

**执行内容**（两步）：
1. **编写测试代码**：为Service层编写单元测试，覆盖核心业务方法（正常流程+异常流程+边界条件）
2. **执行单元测试**：使用 `bash` 工具执行 `mvn test`，运行单元测试并收集结果

**后端单元测试规范**：
- 框架：JUnit 5 + Mockito
- 测试文件位置：`src/test/java/com/xiaomi/mimo/{service}/`
- 命名规范：`{ClassName}Test.java`
- 覆盖范围：核心业务方法（正常流程+异常流程+边界条件）
- 覆盖目标：行覆盖率≥80%，分支覆盖率≥70%

**执行后处理**：单元测试完成后，再次展示交互式选项（排除「编写单元测试」选项）

### 设计符合性检查（阶段4迭代版）

**检查时机**：后端编码完成后、代码质量检查之前

**检查内容**：
- 代码结构是否与设计文档一致（目录、包名、模块）
- 实体类是否与数据库设计一致（表名、字段名、类型）
- API接口是否与API设计一致（路径、方法、参数、响应）
- 服务层是否与业务流程设计一致
- 命名规范是否与技术决策一致

**输出文件**：`$CHECK_DIR/04-review-task-{编号}-backend.md`

**检查结果处理**：
- 有不符合项 → 列出不符合项，提示修正
- 全部符合 → 再次展示交互式选项（排除「设计符合性审查」）

### 代码质量检查（阶段5迭代版）

**触发方式**：用户选择「代码质量审查」选项

**检查内容**：
- **编译检查（必须由agent执行）**：使用 `bash` 工具执行 `mvn clean compile`，验证代码是否能通过编译
- 阿里Java手册违规检查（Blocker/Critical级别）：
  - 硬编码密码、SQL注入风险、空指针未处理
  - 事务边界错误、异常处理不当
  - 命名不规范、魔法值

**执行规范**：
- 编译验证必须由agent通过 `bash` 工具执行，不能要求用户在本地手动执行
- 如果编译失败，分析错误原因并修正代码
- 执行结果记录到审查报告中
- **异常处理**：如果Maven因网络问题或依赖下载超时，记录失败原因到报告中，并提示用户在本地网络环境下执行 `mvn clean compile` 验证编译

**输出文件**：`$CHECK_DIR/05-quality-task-{编号}-backend.md`

**检查结果处理**：
- 有 Blocker/Critical → 列出问题，提示修正
- 无 Blocker/Critical → 再次展示交互式选项（排除「代码质量审查」，保留「编写单元测试」选项供用户选择）

### 迭代完成判定

一个TASK的后端+前端都完成，且用户选择「继续下一个TASK」或「进入最终审查」，才算该迭代完成。
**注意**：允许用户跳过审查直接进入下一个TASK。

### 全部迭代完成

所有TASK的后端+前端都完成后，用户选择「进入最终审查」，进入阶段6测试覆盖率+阶段7交付汇总。

### 迭代顺序

默认迭代顺序：TASK-001 → TASK-002 → TASK-003 → ...

每个TASK的推荐开发顺序：后端 → 前端（确保API就绪后再开发前端页面）

## 设计方案遵循检查清单

- 目录结构是否与设计文档一致
- 模块划分是否与设计文档一致
- 接口定义是否与 API 设计文档一致
- 数据模型是否与数据库设计文档一致
- 命名规范是否与设计文档一致
- 技术选型是否与设计文档一致
- 如发现不一致，必须停止开发并询问架构师

## Bug修复与功能补全

### Bug修复（--type=bugfix）

1. 读取Bug修复工作包，了解bug信息、复现步骤、根因分析、修复方案
2. 定位问题代码
3. 实施修复
4. 补充测试用例
5. 按 `templates/spec-coding.md` 自检清单逐项确认

异常处理：
- Bug无法复现 → 用 `question` 工具向PM报告
- 修复引入新bug → 暂停修复，用 `question` 工具向架构师报告
- 架构师未执行 → 用 `question` 工具提醒用户先执行架构师角色

### 功能补全（--type=completion）

1. 读取功能补全工作包，了解缺失功能、现有实现分析、补全方案
2. 分析现有实现
3. 实施补全
4. 补充测试用例
5. 按 `templates/spec-coding.md` 自检清单逐项确认

异常处理：
- 补全功能与现有设计冲突 → 暂停开发，用 `question` 工具向架构师报告
