# 研发角色操作指南

> 本文档是 SKILL.md 的详细说明，执行时请以 SKILL.md 为准。

## 前置条件检查（必须执行）

在开始编码前，研发角色必须检查以下前置条件：

### 检查清单

1. **架构类型已确认**：`$CHECK_DIR/00-env/architecture-decision.md` 存在
2. **设计文档已生成**：`$DESIGN_DIR` 下有实际设计文档（排除模板文件）或 `$PLANS_DIR/DES-*.md` 存在
3. **代码框架已搭建**：项目目录结构、基础配置已就绪

### 不满足时的处理

- 若架构类型未确认：用 `question` 工具提醒用户先执行架构师角色完成阶段 0 步骤 4
- 若设计文档未生成：用 `question` 工具提醒用户先执行架构师角色完成阶段 2/3
- 若代码框架未搭建：用 `question` 工具提醒用户先执行架构师角色完成阶段 3

## 框架边界识别

1. 查看架构师提供的框架使用说明，了解目录结构、模块职责、开发规范
2. 识别框架层和业务层的边界：
   - **后端**：框架层（common、config、utils、mapper）由架构师维护；业务层（service、controller、entity、dto、vo）由研发人员实现
   - **前端**：框架层（src/router、src/stores、src/api、src/utils、src/components/common）由架构师维护；业务层（src/views、src/components/business）由前端开发实现
   - **移动端**：框架层由架构师在开发任务设计中指定；业务层由移动端开发实现
3. 框架层代码由架构师维护，业务层代码由研发人员实现

## 开发流程（严格按照设计方案）

1. 在架构师搭建的代码框架基础上，**严格按照设计方案**实现业务功能
   - 设计依据优先级：`$PLANS_DIR/DES-*.md`（开发任务设计）> `$DESIGN_DIR`（系统设计）
   - 两者同时存在时以开发任务设计为准；两者都不存在时，必须等待架构师完成设计
2. 遵循框架的目录结构、命名规范、编码规范
3. 使用框架提供的公共组件和工具类，避免重复造轮子
4. **不得偏离设计方案**：如设计方案规定使用 MyBatis-Plus，则不得擅自改用 JPA

## 框架调整请求

1. 如需调整框架结构，需与架构师协商
2. 通过 `question` 工具向架构师提出调整请求，说明调整原因和预期效果
3. 架构师评估影响后，决定是否调整框架
4. **未经架构师同意，不得擅自调整任何设计决策**

## 沟通机制

1. 遇到框架相关问题时，及时与架构师沟通
2. 通过 `question` 工具向架构师提问，架构师需及时响应
3. 重要问题需记录在 `$CHECK_DIR/` 目录下，便于追溯

## 迭代级审查（强制）

> **核心原则**：每个开发任务（TASK-XXX）是一个迭代。编码完成后，使用 `ui-standards §1.15` 模板展示交互式选项，让用户选择下一步操作。

### 完整迭代流程

```
后端/前端编码 → 展示交互式选项（§1.15） → 根据选择执行对应操作
```

### 交互式选项（使用 §1.15 模板）

**询问时机**：编码完成后

**询问模板**：使用 `ui-standards §1.15` TASK完成后下一步选择模板

**选项执行逻辑**：

| 选项 | 执行动作 | 完成后处理 |
|------|----------|-----------|
| 设计符合性审查（推荐） | 执行设计符合性审查 | 移除「设计符合性审查」选项 |
| 代码质量审查 | 执行代码质量审查 | 移除「代码质量审查」选项 |
| 编写单元测试 | 执行单元测试 | 移除「编写单元测试」选项 |
| 继续下一个TASK | **允许跳过审查**，直接进入下一个TASK | 进入下一个TASK |
| 进入最终审查 | **允许跳过审查**，直接进入阶段6+7 | 进入最终审查 |
| 暂停流水线 | 保存当前状态 | 流水线暂停 |

**推荐流程顺序**：设计符合性审查 → 代码质量审查 → 编写单元测试

### 0. 单元测试（可选，由研发人员决定）

**触发方式**：用户在交互式选项中选择「编写单元测试」

**执行内容**（两步）：
1. **编写测试代码**：为核心组件和API模块编写单元测试
2. **执行单元测试**：运行测试并收集结果

**后端单元测试规范**：
- 框架：JUnit 5 + Mockito
- 测试文件位置：`src/test/java/com/xiaomi/mimo/{service}/`
- 命名规范：`{ClassName}Test.java`
- 覆盖范围：核心业务方法（正常流程+异常流程+边界条件）
- 覆盖目标：行覆盖率≥80%，分支覆盖率≥70%

**前端单元测试规范**：
- 框架：Vitest + Vue Test Utils
- 测试文件位置：`src/__tests__/` 或 `tests/`
- 命名规范：`{ComponentName}.spec.ts` 或 `{ModuleName}.spec.ts`
- 覆盖范围：核心组件、API模块

**执行后处理**：单元测试完成后，再次展示交互式选项（排除「编写单元测试」选项）

### 1. 设计符合性检查（阶段4迭代版）

**检查时机**：后端/前端编码完成后、代码质量检查之前

**后端设计符合性检查内容**：
- 代码结构是否与设计文档一致（目录、包名、模块）
- 实体类是否与数据库设计一致（表名、字段名、类型）
- API接口是否与API设计一致（路径、方法、参数、响应）
- 服务层是否与业务流程设计一致
- 命名规范是否与技术决策一致

**前端设计符合性检查内容**：
- 页面路由是否与前端设计一致
- 组件结构是否与前端设计一致
- API调用是否与后端接口定义对齐
- 状态管理是否与前端设计一致
- 权限控制是否与设计一致

**输出文件**：`$CHECK_DIR/04-review-task-{编号}-{backend|frontend}.md`

**检查结果处理**：
- 有不符合项 → 列出不符合项，提示修正
- 全部符合 → 再次展示交互式选项（排除「设计符合性审查」）

### 2. 代码质量检查（阶段5迭代版）

**触发方式**：用户选择「代码质量审查」选项

**检查时机**：设计符合性检查通过后、询问下一步之前

**后端代码质量检查内容**：
- 编译检查：`mvn clean compile` 是否通过
- 阿里Java手册违规检查（Blocker/Critical级别）：
  - 硬编码密码、SQL注入风险、空指针未处理
  - 事务边界错误、异常处理不当
  - 命名不规范、魔法值

**前端代码质量检查内容**：
- TypeScript检查：`vue-tsc --noEmit` 是否通过
- ESLint检查：`npm run lint` 是否通过
- 组件规范检查：是否使用Composition API、TypeScript类型是否正确

**输出文件**：`$CHECK_DIR/05-quality-task-{编号}-{backend|frontend}.md`

**检查结果处理**：
- 有 Blocker/Critical → 列出问题，提示修正
- 无 Blocker/Critical → 再次展示交互式选项（排除「代码质量审查」，保留「编写单元测试」选项供用户选择）

### 3. 迭代完成判定

一个TASK的后端+前端都完成，且用户选择「继续下一个TASK」或「进入最终审查」，才算该迭代完成。
**注意**：允许用户跳过审查直接进入下一个TASK。

### 4. 全部迭代完成

所有TASK的后端+前端都完成后，用户选择「进入最终审查」，进入阶段6测试覆盖率+阶段7交付汇总。

### question 模板

**使用 §1.15 模板**：编码完成后，使用 `ui-standards §1.15` TASK完成后下一步选择模板展示交互式选项。

**选项动态排除**：根据用户选择，排除已完成的选项（详见 §1.15 说明）。

### 迭代顺序

默认迭代顺序：TASK-001 → TASK-002 → TASK-003 → TASK-004 → TASK-005 → TASK-006

每个TASK的推荐开发顺序：后端 → 前端（确保API就绪后再开发前端页面）

## 设计方案遵循检查清单

- 目录结构是否与设计文档一致
- 模块划分是否与设计文档一致
- 接口定义是否与 API 设计文档一致
- 数据模型是否与数据库设计文档一致
- 命名规范是否与设计文档一致
- 技术选型是否与设计文档一致
- 如发现不一致，必须停止开发并询问架构师
