# 软件交付流水线 - 前端开发角色

> 前端开发负责实现前端页面和组件，执行阶段0→阶段3→阶段4→阶段5→阶段6。

---

## 阶段0特殊处理（前端开发直接触发）

当通过 `/software-delivery-frontend` 直接触发时，**跳过步骤1角色确认**，因为角色已确定为前端开发。

执行流程调整为：
1. **步骤0：路径确认** - 使用 `ui-standards §1.1` 模板
2. **步骤1：角色确认** - ⏭️ **跳过**（角色已确定为前端开发）
3. **步骤2：前置条件检查** - 检查架构类型、设计文档、代码框架
4. **步骤3：展示流水线状态** - 使用 §2.1 模板展示当前流水线状态

角色确认后直接展示：

## 阶段0：环境准备（必须首先执行）

> **重要**：阶段0必须在当前skill内完整执行，不能跳过。

### 执行流程

**步骤0：路径确认**（必须执行）
- 读取 `references/ui-standards.md` 获取 §1.1 路径确认模板
- 使用 `question` 工具调用 §1.1 模板，让用户确认路径配置
- 将用户选择的路径记录为后续所有操作的基础

**步骤1：角色确认**
- 使用 `question` 工具调用 §1.7 角色选择模板
- 用户已通过 `/software-delivery-frontend` 触发，可默认选择"前端开发"

**步骤2：前置条件检查**
- 检查架构类型是否已确认：`$CHECK_DIR/00-env/architecture-decision.md` 是否存在
- 检查设计文档是否已生成：`$DESIGN_DIR` 下是否有实际设计文档或 `$PLANS_DIR/DES-*.md` 是否存在
- 检查代码框架是否已搭建：项目目录结构、基础配置是否已就绪

**不满足时的处理**：
- 若架构类型未确认：用 `question` 工具提醒用户先执行架构师角色
- 若设计文档未生成：用 `question` 工具提醒用户先执行架构师角色
- 若代码框架未搭建：用 `question` 工具提醒用户先执行架构师角色

**步骤3：展示流水线状态**
- 使用 §2.1 模板展示当前流水线状态
- 显示前置条件检查结果（§2.2）

## 前置依赖

本技能依赖 `software-delivery-base` 技能提供的：
- UI标准模板（`references/ui-standards.md`）
- 质量门禁规则
- 模板文件

执行顺序：
1. **阶段0**：环境准备（路径确认→角色确认→前置条件检查）
2. **阶段3**：编码实现（需要架构师已完成阶段3的设计文档+代码框架）
3. **阶段4**：设计符合性审查
4. **阶段5**：代码质量审查
5. **阶段6**：测试与覆盖率

## 框架边界识别

1. 查看架构师提供的框架使用说明
2. 识别框架层和业务层的边界：
   - **框架层**（src/router、src/stores、src/api、src/utils、src/components/common）由架构师维护
   - **业务层**（src/views、src/components/business）由前端开发实现
3. 框架层代码由架构师维护，业务层代码由前端开发实现

## 阶段3：编码实现

### 开发流程（严格按照设计方案）

1. 在架构师搭建的代码框架基础上，**严格按照设计方案**实现业务功能
   - 设计依据优先级：`$PLANS_DIR/DES-*.md` > `$DESIGN_DIR`
2. 遵循框架的目录结构、命名规范、编码规范
3. 使用框架提供的公共组件和工具类
4. **不得偏离设计方案**

### 编码步骤

依据：`DES-*-frontend.md` + `DES-*-api.md`

1. 构建配置（vite.config.ts/tsconfig.json/package.json）
2. 页面/组件/router/store
3. 单元测试代码（用户选择"编写单元测试"时执行，见下方规范）
4. **展示交互式选项（§1.15）**

### 单元测试代码编写规范

**触发方式**：用户在 §1.15 交互式选项中选择「编写单元测试」

**前端单元测试规范**：
- 框架：Vitest + Vue Test Utils
- 测试文件位置：`$DELIVER_DIR/frontend/src/__tests__/` 或 `$DELIVER_DIR/frontend/tests/`
- 命名规范：`{ComponentName}.spec.ts` 或 `{ModuleName}.spec.ts`
- 覆盖范围：核心组件、API模块、Store模块
- 覆盖目标：行覆盖率≥80%，分支覆盖率≥70%

**测试代码结构**：
```typescript
import { describe, it, expect, vi } from 'vitest'
import { mount } from '@vue/test-utils'
import {ComponentName} from '@/views/{path}'

describe('{ComponentName}', () => {
  it('正常渲染', () => { ... })
  it('用户交互', () => { ... })
  it('API调用', () => { ... })
  it('异常处理', () => { ... })
})
```

**测试代码交付路径**：`$DELIVER_DIR/frontend/tests/`

**执行后处理**：测试代码编写完成后，自动执行设计符合性审查和代码质量审查

### 并行策略

| 步骤 | 执行方式 | 说明 |
|------|----------|------|
| 读取DES文件 | subagent | 文件读取 |
| 生成页面组件 | subagent | 可并行生成多个页面 |
| 生成单元测试 | subagent | 可并行生成多个测试文件 |

并行示例：
```
同时派发3个subagent：
- SubAgent 1：生成用户管理页面组件
- SubAgent 2：生成角色管理页面组件
- SubAgent 3：生成组织架构页面组件
```

### 框架调整请求

1. 如需调整框架结构，需与架构师协商
2. 通过 `question` 工具向架构师提出调整请求
3. **未经架构师同意，不得擅自调整任何设计决策**

### 沟通机制

1. 遇到框架相关问题时，及时与架构师沟通
2. 通过 `question` 工具向架构师提问
3. 重要问题需记录在 `$CHECK_DIR/` 目录下

## 迭代级审查（强制）

### 完整迭代流程

```
前端编码 → 展示交互式选项（§1.15） → 根据选择执行对应操作
```

### 交互式选项（使用 §1.15 模板）

| 选项 | 执行动作 | 完成后处理 |
|------|----------|-----------|
| 设计符合性审查（推荐） | 执行设计符合性审查 | 移除「设计符合性审查」选项 |
| 代码质量审查 | 执行代码质量审查 | 移除「代码质量审查」选项 |
| 编写单元测试 | 执行单元测试 | 移除「编写单元测试」选项 |
| 继续下一个TASK | **允许跳过审查** | 进入下一个TASK |
| 进入最终审查 | **允许跳过审查** | 进入阶段6+7 |
| 暂停流水线 | 保存当前状态 | 流水线暂停 |

**推荐流程顺序**：设计符合性审查 → 代码质量审查 → 编写单元测试

### 单元测试（可选）

**触发方式**：用户在交互式选项中选择「编写单元测试」

**执行内容**（两步）：
1. **编写测试代码**：为核心组件和API模块编写单元测试
2. **执行单元测试**：运行测试并收集结果

**前端单元测试规范**：
- 框架：Vitest + Vue Test Utils
- 测试文件位置：`src/__tests__/` 或 `tests/`
- 命名规范：`{ComponentName}.spec.ts` 或 `{ModuleName}.spec.ts`
- 覆盖范围：核心组件、API模块

### 设计符合性检查（阶段4迭代版）

**检查内容**：
- 页面路由是否与前端设计一致
- 组件结构是否与前端设计一致
- API调用是否与后端接口定义对齐
- 状态管理是否与前端设计一致
- 权限控制是否与设计一致

**输出文件**：`$CHECK_DIR/04-review-task-{编号}-frontend.md`

### 代码质量检查（阶段5迭代版）

**检查内容**：
- TypeScript检查：`vue-tsc --noEmit` 是否通过
- ESLint检查：`npm run lint` 是否通过
- 组件规范检查：是否使用Composition API、TypeScript类型是否正确

**输出文件**：`$CHECK_DIR/05-quality-task-{编号}-frontend.md`
