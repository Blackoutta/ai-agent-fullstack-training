> 移动端开发负责实现移动端应用，执行阶段0→阶段3→阶段4→阶段5→阶段6。

---

## 阶段0特殊处理（移动端开发直接触发）

当通过 `/software-delivery-mobile` 直接触发时，**跳过步骤1角色确认**，因为角色已确定为移动端开发。

执行流程调整为：
1. **步骤0：路径确认** - 使用 `ui-standards §1.1` 模板
2. **步骤1：角色确认** - ⏭️ **跳过**（角色已确定为移动端开发）
3. **步骤2：前置条件检查** - 检查架构类型、设计文档、代码框架
4. **步骤3：展示流水线状态** - 使用 §2.1 模板展示当前流水线状态

角色确认后直接展示：

## 阶段3：编码实现

### 开发流程

1. 在架构师搭建的代码框架基础上，**严格按照设计方案**实现业务功能
2. 遵循框架的目录结构、命名规范、编码规范
3. **不得偏离设计方案**

### 编码步骤

依据：`DES-*-mobile.md` + `DES-*-api.md`

1. 页面/组件/导航
2. 构建配置
3. 单元测试代码（用户选择"编写单元测试"时执行，见下方规范）
4. **展示交互式选项（§1.15）**

> 注：具体技术栈由设计文档指定（Flutter/React Native/原生等）

### 单元测试代码编写规范

**触发方式**：用户在 §1.15 交互式选项中选择「编写单元测试」

**移动端单元测试规范**：
- Flutter：flutter_test + mockito
- React Native：Jest + @testing-library/react-native
- 原生Android：JUnit + Mockito + Espresso
- 原生iOS：XCTest + Quick/Nimble
- 测试文件位置：按技术栈约定（如 Flutter 的 `test/` 目录）
- 覆盖范围：核心组件、API模块
- 覆盖目标：行覆盖率≥80%，分支覆盖率≥70%

**测试代码交付路径**：`$DELIVER_DIR/mobile/tests/`

**执行后处理**：测试代码编写完成后，自动执行设计符合性审查和代码质量审查

### 并行策略

| 步骤 | 执行方式 | 说明 |
|------|----------|------|
| 读取DES文件 | subagent | 文件读取 |
| 生成页面组件 | subagent | 可并行生成多个页面 |
| 生成单元测试 | subagent | 可并行生成多个测试文件 |

### 框架调整请求

如需调整框架结构，通过 `question` 工具向架构师提出调整请求。**未经架构师同意，不得擅自调整。**

## 迭代级审查（强制）

### 完整迭代流程

```
移动端编码 → 展示交互式选项（§1.15） → 根据选择执行对应操作
```

### 交互式选项（使用 §1.15 模板）

| 选项 | 执行动作 | 完成后处理 |
|------|----------|-----------|
| 编写单元测试 | 执行单元测试 → 自动执行设计符合性审查 → 自动执行代码质量审查 | 移除已完成选项 |
| 设计符合性审查 | 执行设计符合性审查 → 自动执行代码质量审查 | 移除已完成选项 |
| 代码质量审查 | 仅执行代码质量审查 | 移除已完成选项 |
| 继续下一个TASK | **允许跳过审查** | 进入下一个TASK |
| 进入最终审查 | **允许跳过审查** | 进入阶段6+7 |
| 暂停流水线 | 保存当前状态 | 流水线暂停 |

### 单元测试（可选）

- 框架：按技术栈指定（Flutter: flutter_test, React Native: Jest, etc.）
- 覆盖范围：核心组件、API模块

### 设计符合性检查（阶段4迭代版）

**检查内容**：
- 页面路由是否与移动端设计一致
- 组件结构是否与移动端设计一致
- API调用是否与后端接口定义对齐
- 状态管理是否与设计一致

**输出文件**：`$CHECK_DIR/04-review-task-{编号}-mobile.md`

### 代码质量检查（阶段5迭代版）

**检查内容**：
- 按技术栈对应规范审查
- Lint/静态分析检查
- 单元测试检查

**输出文件**：`$CHECK_DIR/05-quality-task-{编号}-mobile.md`
