# Spec Coding 规范模板

> **定位**：本文件是规范参考文档，非输出模板。用于指导 PM 和架构师编写工作包和开发任务设计时的格式规范。
> **引用场景**：`bugfix-completion-flow.md` 的自检步骤、`work-package-template.md` 的注释。

PM 和架构师在编写工作包和开发任务设计时，参考以下模板格式。

## 模板一：OpenAPI 风格（适合 API 开发）

```markdown
## API：POST /api/v1/users

### 基本信息
- **端点**：`/api/v1/users`
- **方法**：POST

### 请求参数
| 字段     | 类型   | 必填 | 约束                        | 示例             |
| -------- | ------ | ---- | --------------------------- | ---------------- |
| email    | string | 是   | 邮箱格式                    | user@example.com |
| password | string | 是   | 8-32 字符，包含大小写和数字 | -                |

### 响应格式
- **201 Created**：用户创建成功
  ```json
  { "user_id": "uuid", "email": "user@example.com" }
  ```
- **409 Conflict**：邮箱已存在
  ```json
  { "code": "EMAIL_ALREADY_EXISTS", "message": "邮箱已被注册" }
  ```

### 验收标准
- [ ] 密码用 bcrypt，cost=12
- [ ] 邮箱唯一性由数据库唯一索引保证
- [ ] 分支覆盖率 >= 70%
```

## 模板二：Gherkin 风格（适合 BDD）

```markdown
Feature: 用户登录

  Scenario: 使用有效凭据登录
    Given 用户已注册邮箱 "test@example.com" 和密码 "Password123"
    When 用户提交登录请求
    Then 返回 200 状态码和 JWT token
    And token 有效期 24 小时
```

## 模板三：Checklist 风格（适合代码审查）

```markdown
## Code Review Checklist

### 功能性
- [ ] 实现符合 Spec 描述
- [ ] 边界条件已处理：空值、越界、并发
- [ ] 错误处理完善

### 质量
- [ ] 函数长度 <= 50 行
- [ ] 圈复杂度 <= 10
- [ ] 无重复代码（DRY）

### 安全
- [ ] 无敏感信息硬编码
- [ ] 输入已验证/转义
- [ ] 权限检查已加
```

## 三色标签（AI 权限控制）

| 标签 | 含义 | 示例 |
|------|------|------|
| ✅ Always | AI 自动执行 | 跑 lint、跑测试、格式化代码 |
| ⚠️ Ask First | 需用户确认 | 改数据库索引、改 API 路径、改公共组件 |
| 🚫 Never | 绝对禁止 | 直连生产库、提交密钥、删线上数据 |

## 自检清单（每个工作包完成后必须执行）

### 代码质量（通用）
- [ ] 所有 API 错误返回符合统一格式
- [ ] 边界条件已处理（空值、越界、并发）
- [ ] 单元测试覆盖正常/异常/边界场景
- [ ] 分支覆盖率 >= 70%
- [ ] 无敏感信息硬编码（密码、token、密钥）
- [ ] 日志不打印 token、password、api key

### 后端专属
- [ ] 数据库查询命中指定索引
- [ ] SQL 无慢查询风险
- [ ] 事务边界合理

### 前端专属
- [ ] 用户输入已做 XSS 防护/校验
- [ ] 组件 props 类型定义完整
- [ ] API 调用统一封装在 api/ 层
- [ ] 路由守卫/权限控制已实现

### 框架协作
- [ ] 在架构师搭建的代码框架基础上实现业务功能
- [ ] 遵循框架的目录结构、命名规范、编码规范
- [ ] 未擅自修改框架结构

哪项无法确认，必须写原因，不能糊弄。
