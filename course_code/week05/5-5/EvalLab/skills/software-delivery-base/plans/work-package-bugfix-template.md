# Bug 修复工作包模板（Bugfix WP Template）

> PM 或研发角色在创建 bug 修复工作包时使用。相比功能开发工作包，bugfix 工作包更关注问题定位和修复验证。

```markdown
# WP-XXX-fix-<bug简述>

## 1. Bug 信息

| 属性 | 值 |
|------|-----|
| Bug 编号 | <BUG-XXX 或 Issue 编号> |
| 严重程度 | <Blocker/Critical/Major/Minor> |
| 优先级 | <P0-紧急/P1-高/P2-中/P3-低> |
| 影响版本 | <版本号> |
| 发现日期 | YYYY-MM-DD |
| 负责角色 | <后端开发/前端开发/移动端开发/数据库工程师/测试/运维> |

## 2. 问题描述

### 现象
<描述用户可见的错误现象，包含错误信息>

### 影响范围
- 影响功能：<哪些功能受影响>
- 影响用户：<全部用户/特定角色/特定条件>
- 影响环境：<生产/测试/开发>

## 3. 复现步骤

1. <步骤1：前置条件>
2. <步骤2：操作动作>
3. <步骤3：触发条件>
4. <步骤4：观察到的错误现象>

**复现概率**：<必现/偶现（X%）/特定条件触发>

## 4. 根因分析

### 直接原因
<代码层面的直接错误>

### 根本原因
<导致问题产生的深层原因>

### 相关代码
- 文件：<path/to/file.java>
- 行号：<L100-L120>

## 5. 修复方案

### 修复策略
<简述修复思路>

### 修改范围
| 文件 | 修改类型 | 说明 |
|------|---------|------|
| path/to/file.java | 修改 | <具体修改内容> |
| path/to/test.java | 新增 | <测试用例> |

### 风险评估
- 影响范围：<本次修改是否可能引入新问题>
- 回归风险：<高/中/低>
- 需要额外测试：<哪些功能需要回归测试>

## 6. 验收标准（可勾选）

- [ ] Bug 已修复：原始复现步骤不再触发错误
- [ ] 边界条件已处理：相关边界场景已覆盖
- [ ] 单元测试已补充：新增/修改的代码有对应测试
- [ ] 回归测试通过：受影响功能的回归测试通过
- [ ] 无新问题引入：未引入新的 bug 或性能问题
- [ ] 代码审查通过：符合代码规范和设计要求

## 7. 三色权限标签

- ✅ Always：<AI 可自动执行>
- ⚠️ Ask First：<需用户确认>
- 🚫 Never：<禁止>

## 8. 关联信息

- 关联工作包：<如果有相关功能开发工作包>
- 关联设计文档：<如果有相关设计文档>
```

## 填写说明

1. **Bug 信息**：完整记录 bug 的基本信息，便于追踪
2. **问题描述**：清晰描述现象和影响范围
3. **复现步骤**：详细的复现步骤是验证修复的基础
4. **根因分析**：区分直接原因和根本原因
5. **修复方案**：明确修改范围和风险评估
6. **验收标准**：可勾选的验收项
7. **三色标签**：明确 AI 执行权限

## 命名规范

- 文件名格式：`WP-XXX-fix-<bug简述>.md`
- 示例：`WP-005-fix-用户登录空指针.md`

## 与功能开发工作包的区别

| 维度 | 功能开发工作包 | Bug 修复工作包 |
|------|--------------|--------------|
| 重点 | 新功能实现 | 问题定位与修复 |
| 接口契约 | 中等/大任务必填 | 仅在涉及接口变更时填写 |
| 数据模型 | 中等/大任务必填 | 仅在涉及表结构变更时填写 |
| 复现步骤 | 不需要 | 必须详细填写 |
| 根因分析 | 不需要 | 必须填写 |
