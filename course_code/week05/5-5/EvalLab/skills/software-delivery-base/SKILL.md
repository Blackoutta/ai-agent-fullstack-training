# 软件交付流水线 - 共享基础设施

> 本技能是 software-delivery 各角色技能的共享基础，提供环境准备、UI标准、质量门禁、模板等共用能力。
> **不直接触发**，由各角色技能引用。

---

## 1. 参数速查

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--type` | `feature` | `feature`（新功能）/ `bugfix`（Bug修复）/ `completion`（功能补全）。含"修复/hotfix/bug"→bugfix；含"补全/缺失"→completion；其他→feature |
| `--arch` | `monolith` | `monolith` / `microservice`（架构师确认） |
| `--deliver-dir` | `<工程根>/deliverables/` | 交付产物输出目录 |
| `--check-dir` | `<工程根>/check/` | 审查报告输出目录 |
| `--plans-dir` | `<工程根>/plans/` | 工作包/开发任务计划输出目录 |
| `--requirements-dir` | `<工程根>/requirements/` | 需求文档输入目录 |
| `--config-dir` | `<工程根>/config/` | 中间件配置输入目录 |
| `--design-dir` | `<工程根>/design/` | 系统级设计文档目录 |

## 2. 执行流程总览

```
阶段0: 环境准备 → 阶段1: 需求拆分(PM) → 阶段2: 开发任务计划(PM+架构师)
                                    ↓
                    阶段3: 编码实现(架构师设计+框架 → 研发角色编码)
                                    ↓
                    阶段4: 设计符合性审查 → 阶段5: 代码质量审查
                                    ↓
                    阶段6: 测试与覆盖率 → 阶段7: 交付汇总
```

### 角色与执行阶段

| 角色 | 执行阶段 | 核心职责 |
|------|---------|---------|
| PM | 0→1→2 | 需求拆分、开发任务规划 |
| 架构师 | 0→2→3（设计+脚手架）→最终审查（4→5） | 架构确认、设计文档、代码框架、最终全量审查 |
| 后端开发 | 0→3→4→5→6 | 后端业务代码、单元测试 |
| 前端开发 | 0→3→4→5→6 | 前端页面组件、单元测试 |
| 移动端开发 | 0→3→4→5→6 | 移动端应用、单元测试 |
| 数据库工程师 | 0→3→4→5 | SQL设计与优化 |
| 测试 | 0→6 | 集成测试、验收测试 |
| 运维 | 0→3→7 | CI/CD、容器化、监控（配置文件，无需设计符合性/代码质量审查） |

### 强制规则

1. 架构师必须先完成设计（阶段3），其他研发角色才能开始编码。
2. 阶段间严格顺序执行，除 bugfix/completion 模式允许跳过阶段1/2的PM部分。
3. 阶段3前置条件：架构类型✓ 开发任务计划（TASK-*.md）✓（设计文档和代码框架由阶段3生成）

### 角色间交接机制

各角色完成自身阶段后，通过以下机制通知下一角色：

| 交接点 | 当前角色 | 下一角色 | 交接方式 |
|--------|---------|---------|---------|
| 阶段2完成 | PM | 架构师 | 更新 `$CHECK_DIR/00-env/pipeline-status.md`，展示阶段完成提示，提示用户切换到架构师角色 |
| 阶段3设计完成 | 架构师 | 研发角色 | 更新 `$CHECK_DIR/00-env/pipeline-status.md`，展示框架交付确认，提示用户切换到研发角色 |
| 阶段3编码完成 | 研发角色 | 测试/架构师 | 更新 `$CHECK_DIR/00-env/pipeline-status.md`，展示迭代完成提示，用户选择进入阶段6或继续下一个TASK |
| 阶段4/5完成 | 架构师 | 测试 | 更新 `$CHECK_DIR/00-env/pipeline-status.md`，展示审查完成提示，提示用户切换到测试角色 |
| 阶段6完成 | 测试 | 运维 | 更新 `$CHECK_DIR/00-env/pipeline-status.md`，展示测试完成提示，提示用户切换到运维角色执行阶段7 |

**交接规范**：
1. 当前角色完成阶段后，必须更新 `pipeline-status.md`
2. 展示 `ui-standards §5.2` 阶段完成提示
3. 在完成提示中明确指出下一步应执行的角色和阶段
4. 用户手动切换角色后，新角色通过前置条件检查确认交接完成

**PM专用交接规则**（强制）：
- PM完成后，角色切换界面**仅显示架构师选项**
- 其他研发角色全部隐藏（架构师必须先完成设计，其他角色才能编码）
- 使用 `ui-standards §1.16` PM专用模板

## 3. 阶段0：环境准备（所有角色共用）

> **执行模式**：阶段0由主 agent 直接执行（因涉及 question 交互），非交互的文件操作可委托 subagent。

### 强制规则

1. **路径必须有依据**：agent 使用任何路径之前，必须有明确来源（环境信息中的 Working directory、上下文中的用户指令、已读取的文件系统、或 memory 中的记录）。禁止在无任何依据的情况下假设或编造路径。
2. **路径发现策略**：若上下文已有路径信息（如阶段0已完成、断点续做、用户指定），直接使用，无需重复询问。若路径未知，先用 `read` 探测工程根目录，再通过 `question` 工具（ui-standards §1.1）与用户确认。
3. **确认后才可操作**：路径确定后，才可读取或写入对应目录下的文件。

### 主 agent 执行步骤（交互）

> **路径发现策略**：
> - 若上下文已有路径信息（阶段0已完成、断点续做、用户指定），直接使用，跳过步骤0。
> - 若路径未知，主 agent 必须先用 `read` 工具读取工程根目录（来自环境信息中的 Working directory），探测已有目录，再进入步骤0确认。

1. **步骤0：路径确认**（仅路径未知时执行）
   - 主 agent 用 `read` 工具读取工程根目录，探测已有目录
   - 调用 `question` 工具，使用 `ui-standards §1.1` 路径确认模板
   - 模板中的 `$PROJECT_ROOT` 替换为实际工程根目录路径
   - 逐字复制模板，禁止改写

2. **步骤1：角色确认**
   - 主 agent 调用 `question` 工具，使用 `ui-standards §1.7` 角色选择模板
   - 逐字复制模板，禁止改写

3. **步骤2：环境初始化**（交互部分）
   - 如检测到旧产物，主 agent 调用 `question` 工具 `ui-standards §1.4` 清理确认模板
   - 如用户选择清理 design/，主 agent 调用 `question` 工具 `ui-standards §1.5` 敏感目录清理确认模板

4. **步骤4：范围确认**（交互部分，按角色区分）

   **仅架构师角色执行**：
   - 主 agent 调用 `question` 工具 `ui-standards §1.2` 架构类型确认
   - 如选择微服务，主 agent 调用 `question` 工具 `ui-standards §1.3` 微服务技术栈
   - 将选择记录到 `$CHECK_DIR/00-env/architecture-decision.md`

   **PM角色**：
   - 跳过架构类型确认（由架构师在阶段0/2负责）
   - 如需选择开发任务，调用 `question` 工具 `ui-standards §1.6`

   **研发角色（后端/前端/移动端/DBA/测试/运维）**：
   - 检查 `$CHECK_DIR/00-env/architecture-decision.md` 是否已存在
   - 已存在：直接使用已有决策，跳过询问
   - 不存在：提示用户先执行架构师角色确认架构类型

### subagent 执行步骤（文件操作）

> 主 agent 派发 subagent 执行以下非交互步骤，subagent 读取 `references/env-init-subagent.md` 获取详细指令。

1. **步骤2：环境初始化**（文件操作部分）
   - 创建目录结构
   - 复制模板文件

2. **步骤3：输入收集**
   - 读取输入文档（requirements/）
   - 读取中间件配置（config/）
   - 统计关键指标

3. **步骤5：任务登记**
   - 输出流程检查清单
   - 初始化流水线状态文件

### 主 agent 最终处理

1. 接收 subagent JSON 结果
2. 生成 `$CHECK_DIR/00-env/scope-definition.md`
3. 展示 `ui-standards §2.1` 阶段进度展示
4. 展示 `ui-standards §2.4` 关键指标登记
5. 展示 `ui-standards §2.5` 流程检查清单
6. 进入后续阶段

## 4. 质量门禁

### 硬门禁（需用户显式决策）

| 门禁 | 阈值 | 不达标动作 |
|------|------|-----------|
| 设计符合性 | 100% | 回阶段3修正；3轮后用户决策 |
| 代码规范 | 0 Blocker/Critical | 回阶段3修正；3轮后用户决策 |
| 需求追溯 | 需求→代码覆盖率100% | 回阶段3补全；3轮后用户决策 |
| 安全扫描 | 0高危漏洞 | 回阶段3修正；3轮后用户决策 |

### 软门禁（需用户确认放行）

| 门禁 | 阈值 | 不达标动作 |
|------|------|-----------|
| 行覆盖率 | ≥80% | 回阶段3补测；3轮后用户确认 |
| 分支覆盖率 | ≥70% | 回阶段3补测；3轮后用户确认 |
| 需求→测试覆盖率 | ≥90% | 回阶段6补测；3轮后用户确认 |
| 非功能性需求覆盖 | 100% | 回阶段3补全；3轮后用户决策 |

### 问题分级

| 级别 | 定义 | 示例 |
|------|------|------|
| Blocker | 编译失败、安全漏洞 | SQL注入、硬编码密码 |
| Critical | 功能异常、规范严重违反 | 接口不一致、事务边界错误 |
| Major | 影响可维护性 | 命名不规范、代码重复 |
| Minor | 代码风格偏好 | 缩进风格、空行数量 |

## 5. Bug修复与功能补全

### Bug修复（--type=bugfix）
流程：阶段0 → 阶段3（含迭代级审查） → 阶段4 → 阶段5 → 阶段6（跳过阶段1/2的PM部分，可选执行阶段7）

### 功能补全（--type=completion）
流程：阶段0 → 阶段3（含迭代级审查） → 阶段4 → 阶段5 → 阶段6（跳过阶段1/2的PM部分，可选执行阶段7）

## 6. 注意事项

- **路径必须有依据**：所有路径变量必须有明确来源。若路径未知，先探测再询问；若已知，直接使用无需重复确认。
- **交付产物必须放在 `$DELIVER_DIR` 目录下**：所有代码脚手架、业务代码、单元测试代码必须放在交付目录内，禁止直接放在项目根目录。目录结构：
  - 后端代码：`$DELIVER_DIR/backend/`（含 `src/main/java/` 业务代码 + `src/test/java/` 单元测试）
  - 前端代码：`$DELIVER_DIR/frontend/`（含 `src/` 业务代码 + `tests/` 单元测试）
  - 数据库SQL：`$DELIVER_DIR/sql/`（**禁止放在 `$DELIVER_DIR/ops/sql/`**，SQL 与运维配置分离）
  - 运维配置：`$DELIVER_DIR/ops/`（仅含 Dockerfile、docker-compose、nginx.conf 等）
  - **注意**：`ops/` 下的 docker-compose.yml 挂载 SQL 时需使用相对路径 `../../../sql/init.sql`（从 `ops/docker/` 到 `deliverables/sql/`）
- **严格按照设计方案实现**：违反设计将导致审查不通过
- **输入文档只读**（`$REQUIREMENTS_DIR`）
- **凭据安全**：只放 `*.local.yaml`（已 gitignore），代码用 `${VAR:default}`
- **凭据隔离**：读取 `middleware.local.yaml` 时仅提取参数名，不传入子agent
- **前后端对齐**：前端API必须与后端接口严格对齐
- **代码提交**：由人工负责，AI不执行git操作
- **流水线状态跟踪**：每个阶段完成时，**当前执行角色必须**更新 `$CHECK_DIR/00-env/pipeline-status.md`，将已完成阶段状态从 `⏸️ 待执行` 改为 `✅ 已完成`，将下一阶段状态从 `⏸️ 待执行` 改为 `⏳ 进行中`。此文件是各角色间的状态传递纽带。
- **Subagent并行优先**：在不影响功能和交互界面的情况下，尽量使用subagent并行执行

### 模板编写规范

- **变量格式**：统一使用 `$VAR_NAME` 格式（如 `$DELIVER_DIR`）
- **验收标准**：统一使用 `✅ / ❌` 表示通过/不通过
- **章节编号**：使用 `## N. 标题` 数字编号格式

## 8. Subagent并行执行策略

### 并行执行原则

| 原则 | 说明 |
|------|------|
| **独立性优先** | 无依赖关系的任务可并行执行 |
| **交互隔离** | 涉及question交互的步骤由主agent执行 |
| **结果汇总** | 主agent负责收集、验证、展示subagent结果 |
| **错误处理** | 单个subagent失败不影响其他并行任务 |

### 并行执行限制

| 限制 | 说明 | 应对策略 |
|------|------|----------|
| **最大并行数** | 建议不超过5个subagent | 分批执行 |
| **依赖关系** | 有依赖的任务必须串行 | 按依赖图分层 |
| **交互步骤** | question交互必须主agent执行 | 分离交互与执行 |
| **文件冲突** | 多个subagent写同一文件会冲突 | 明确文件归属 |
| **超时风险** | 并行任务可能超时 | 设置合理超时时间 |

### SubAgent派发模板

```text
任务: 生成 {文档/代码名称}

skills_dir: {skills父目录绝对路径}

读取:
- {输入文件1}
- {输入文件2}

执行:
1. {步骤1}
2. {步骤2}
3. {步骤3}

写入: {输出文件路径}

完成后返回:
- 文件路径
- 生成摘要
- 待确认项（如有）
```

### 最佳实践

1. **识别独立任务**：分析任务依赖关系，找出可并行的任务
2. **合理分组**：将相似任务分组，减少subagent数量
3. **明确边界**：每个subagent负责明确的文件范围
4. **统一接口**：所有subagent返回格式统一（文件路径+摘要+待确认项）
5. **错误隔离**：单个subagent失败不影响其他任务
6. **进度跟踪**：主agent实时跟踪并行任务进度
7. **结果验证**：并行完成后统一验证文件完整性

## 9. 通用触发条件与路由

> 当用户使用通用触发条件时，本技能作为路由器，引导用户选择具体角色技能。

### 通用触发条件

- "根据需求/设计/规范生成代码" / "生成交付产物" / `/software-delivery`
- "修复bug" / "hotfix" / `/software-delivery --type=bugfix`
- "补全功能" / "功能缺失" / `/software-delivery --type=completion`

### 路由逻辑

当用户使用通用触发条件时：

1. 执行阶段0环境准备（本技能负责）
2. 阶段0步骤1（角色确认）时，使用 `ui-standards §1.7` 角色选择模板引导用户选择角色
3. 用户选择角色后，路由到对应的角色技能：
   - PM → `software-delivery-pm`
   - 架构师 → `software-delivery-architect`
   - 后端开发 → `software-delivery-backend`
   - 前端开发 → `software-delivery-frontend`
   - 移动端开发 → `software-delivery-mobile`
   - 数据库工程师 → `software-delivery-dba`
   - 测试 → `software-delivery-tester`
   - 运维 → `software-delivery-ops`

### 触发条件优先级

1. **精确触发**（直接路由）：`/software-delivery-backend` → 直接加载 `software-delivery-backend`
2. **通用触发**（需路由）：`/software-delivery` → 加载 `software-delivery-base` → 角色选择 → 路由到具体技能
