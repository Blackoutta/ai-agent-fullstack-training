# 软件交付流水线 - 测试角色

> 测试负责集成测试和验收测试，执行阶段0→阶段6。
> **阶段6独立所有权**：阶段6（测试与覆盖率）由测试角色独立负责，架构师不直接执行阶段6。测试角色可查看架构师在阶段4/5生成的审查报告作为测试输入。

---

## 阶段0特殊处理（测试直接触发）

当通过 `/software-delivery-tester` 直接触发时，**跳过步骤1角色确认**，因为角色已确定为测试。

执行流程调整为：
1. **步骤0：路径确认** - 使用 `ui-standards §1.1` 模板
2. **步骤1：角色确认** - ⏭️ **跳过**（角色已确定为测试）
3. **步骤2：前置条件检查** - 检查架构类型、代码实现、设计文档
4. **步骤3：展示流水线状态** - 使用 §2.1 模板展示当前流水线状态

角色确认后直接展示：
```
**👤 角色确认**
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
当前角色：测试
执行阶段：阶段0 → 阶段6
核心职责：集成测试、验收测试
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 前置条件检查（必须执行）

1. **架构类型已确认**：`$CHECK_DIR/00-env/architecture-decision.md` 存在
2. **代码已实现**：`$DELIVER_DIR` 下有业务代码
3. **设计文档存在**：`$DESIGN_DIR` 下有设计文档

不满足时用 `question` 工具提醒用户先完成前置阶段。

## 阶段6：测试与覆盖率

### 执行流程

1. 展示 `ui-standards §5.1` 阶段开始提示
2. **检查测试代码是否存在**：
   - 后端：检查 `$DELIVER_DIR/backend/src/test/java/` 下是否有 `*Test.java` 文件
   - 前端：检查 `$DELIVER_DIR/frontend/tests/` 或 `src/__tests__/` 下是否有 `*.spec.ts` 文件
   - 移动端：检查 `$DELIVER_DIR/mobile/tests/` 下是否有测试文件
   - 如果迭代级审查中用户选择跳过单元测试，阶段6仅执行构建验证，不检查覆盖率
3. **运行单元测试并生成覆盖率**：
   - 后端：`mvn clean verify`（生成 Jacoco 覆盖率报告）
   - 前端：`npm run coverage`（生成 Vitest 覆盖率报告）
4. 使用 `templates/test-coverage-report.md` 生成 `$CHECK_DIR/06-coverage.md`
5. 软门禁不达标 → `ui-standards §1.9` 质量门禁放行确认
6. 构建验证：
   - 后端：`mvn clean verify`
   - 前端：`npm run build`
7. 展示 `ui-standards §5.2` 阶段完成提示

### 并行策略

| 步骤 | 执行方式 | 说明 |
|------|----------|------|
| 运行单元测试 | subagent | 可并行运行不同服务的测试 |
| 生成覆盖率报告 | subagent | 依赖测试结果 |
| 构建验证 | subagent | 可并行构建前后端 |

### 质量门禁

#### 软门禁（需用户确认放行）

| 门禁 | 阈值 | 不达标动作 |
|------|------|-----------|
| 行覆盖率 | ≥80% | 回阶段3补测；3轮后用户确认 |
| 分支覆盖率 | ≥70% | 回阶段3补测；3轮后用户确认 |

#### 门禁处理流程

1. 覆盖率达标 → 直接通过
2. 覆盖率不达标 → 展示 `ui-standards §1.9` 质量门禁放行确认模板
3. 用户选择「确认放行」→ 标记为遗留项，继续
4. 用户选择「继续修正」→ 回阶段3补测
5. 轮次达上限（3轮）→ 展示 `ui-standards §4.5` 轮次耗尽，用户决策

### 测试覆盖率报告

使用 `templates/test-coverage-report.md` 生成报告，包含：
- 后端覆盖率（行覆盖率、分支覆盖率）
- 前端覆盖率（行覆盖率、分支覆盖率）
- 移动端覆盖率（如有）
- 覆盖率趋势对比
- 未覆盖模块清单

## 集成测试

### 测试范围

1. **API接口测试**：验证所有API接口的请求/响应格式、状态码、错误处理
2. **业务流程测试**：验证核心业务流程的端到端执行
3. **数据一致性测试**：验证数据库操作的正确性
4. **权限测试**：验证角色权限控制的有效性

### 测试用例编写规范

- 使用 Gherkin 风格或 Checklist 风格（参考 `templates/spec-coding.md`）
- 每个测试用例必须包含：前置条件、执行步骤、预期结果
- 覆盖正常流程、异常流程、边界条件

---

## 验收测试

### 验收标准

1. 所有硬门禁通过（设计符合性100%、代码规范0 Blocker/Critical）
2. 软门禁通过或用户确认放行
3. 核心业务流程可正常执行
4. 无阻塞性Bug

### 验收报告

验收完成后，输出验收结论：
- 通过/不通过
- 遗留问题清单
- 建议改进项
